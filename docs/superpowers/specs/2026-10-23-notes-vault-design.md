# Notes Vault — Design

Date: 2026-10-23
Status: draft, awaiting approval

## Intent

A personal, local-only notes vault. Claude writes the notes; the owner reads
them. Sources are podcast transcripts, YouTube transcripts, and conversations
with Claude. The owner wants to open the vault in a browser, find a note by
searching, skim its key takeaways in under a minute, and expand to the full
writeup on demand.

No server, no database, no framework, no container. Double-click a file and
it works.

## Goals

- Notes are plain Markdown files on disk and remain useful without the viewer.
- A single static HTML page lists, searches, filters, and renders the notes.
- Each note has two layers: a short "glance" (takeaways) shown by default and
  a "full writeup" collapsed behind a click.
- Adding a note is: write the `.md` file, run `build.py`, reload the page.
- Everything works offline, from `file://`, in a current Chrome or Firefox.

## Non-goals

- Editing notes in the browser. Notes are edited as files.
- Syncing, multi-user, auth, cloud, mobile.
- Automatic transcript fetching. For now the owner pastes transcripts or gives
  a link; Claude fetches what it can with its own web tools. Installing tools
  such as `yt-dlp` or Whisper is explicitly deferred.
- Fancy search (fuzzy, ranking, stemming). Substring match is enough.

## Anti-goals (what would make this a failure)

- Needing to start anything (dev server, container, Node process) to read notes.
- A build or runtime dependency that breaks when offline.
- Notes whose content lives only inside generated files. `vault/*.md` is the
  only source of truth; `notes.js` is disposable output.
- A note whose glance is not skimmable in about a minute.

## Constraints

- Machine has Python 3.14 and Node 26. Nothing else may be installed for now.
- `build.py` uses the Python standard library only.
- The viewer runs from `file://`, so it cannot `fetch()` files or list
  directories. All note content must be loaded via `<script src>`.
- Project root is `/home/mihai/work/me/notes`.
- Git is owned by the owner. Claude never runs git commands that change state
  (no init, add, commit, branch, stash, checkout). Read-only commands such as
  `git status`, `git log`, `git diff` are fine.

## Decided: repository layout

```
notes/                       # project root
  index.html                 # the viewer
  viewer.js                  # viewer logic
  style.css                  # viewer styles
  vendor/marked.min.js       # vendored Markdown renderer, pinned version
  notes.js                   # GENERATED by build.py; committed, never hand-edited
  build.py                   # bundles vault/*.md -> notes.js
  vault/                     # one Markdown file per note (source of truth)
  sources/                   # raw transcripts as received; not bundled
  templates/note.md          # blank note template
  CLAUDE.md                  # instructions for future Claude sessions
  docs/superpowers/specs/    # this document and later designs
```

Owner's call: plain HTML/JS, `build.py`, no database, no React.
Claude's calls: the `vault/` name (avoids `notes/notes/`), separate
`viewer.js`/`style.css` files, keeping `notes.js` in the tree so a fresh clone
works without a build. Owner approved vendoring `marked` for Markdown rendering.

## Decided: note file format

File name: `vault/YYYY-MM-DD-<slug>.md`, date = day the note was written.

```markdown
---
title: How to Price a B2B SaaS
source: podcast
url: https://example.com/episode/123
date: 2026-10-23
published: 2026-09-01
author: Lenny Rachitsky
tags: pricing, saas, b2b
---

One or two sentences saying what this source is and why it mattered.

## Takeaways

- Five to ten bullets. Each one a complete, standalone idea.
- Concrete over vague. Numbers, names, and rules of thumb survive; mood does not.

## Full writeup

### Section following the flow of the source
Prose and bullets. Notable quotes as blockquotes with a timestamp when known:

> "Price on value, not cost." (14:32)

### Next section
...
```

Fields: `source` is one of `podcast`, `youtube`, `conversation`. `date` is when
the note was written; `published` (optional) is when the source was published.
`author` (optional) is the show, channel or guest. `tags` are comma-separated
and lowercase.

Rules:

- Front matter is a simple `key: value` block between `---` lines. No YAML
  library; `build.py` parses it by hand. Unknown keys are kept and ignored.
- `title`, `source`, `date` are required. `build.py` fails loudly on a note
  missing any of them, or with an unknown `source` value.
- Everything between the front matter and `## Full writeup` is the glance.
  Everything from `## Full writeup` onward is the full writeup. If the heading
  is absent, the whole body is the glance.
- `conversation` notes follow the same shape; `url` is omitted.
- Target length: glance under ~150 words; full writeup unbounded.

## Decided: build.py

- Run as `python3 build.py` from the project root. No arguments needed.
- Reads every `vault/*.md`, parses front matter, splits glance / full.
- Writes `notes.js` containing `window.NOTES = [...]` with, per note:
  `id` (file name without extension), `title`, `source`, `url`, `date`,
  `published`, `author`, `tags` (array), `glance` (Markdown), `full`
  (Markdown, may be empty), `text` (lowercased plain-ish concatenation of
  title, tags, glance, full, for search).
- Sorted by `date` descending, then title.
- Prints one line per note and a summary count. Non-zero exit and a clear
  message on any invalid note; `notes.js` is not touched on failure.
- Must finish well under a second for a few hundred notes.

## Decided: viewer behaviour

Layout: two panes. Left sidebar: search box, source filter chips
(All / Podcast / YouTube / Conversation), tag list, note list. Right pane:
the selected note.

Note list:

- Newest first. Each row shows title, source badge, date, tags.
- Filters combine: search terms AND source chip AND selected tag.
- Search splits the query on whitespace; every term must appear as a
  substring (case-insensitive) in the note's `text`. Empty query = all notes.
- Live filtering as you type; no submit button.

Note pane:

- Header: title, source badge, date (and published date if present), author,
  tags, and the source link opening in a new tab.
- Glance rendered as Markdown.
- "Show full writeup" button toggles the full writeup; label flips to
  "Hide full writeup". Default collapsed.
- If the current search terms match only inside `full`, the full writeup
  opens automatically for that note.
- Selected note's `id` is stored in the URL hash (`#2026-10-23-slug`) so
  reload and bookmarks return to it. On load with no hash, show the newest
  note.

Keyboard: `/` focuses search; `Escape` clears search and blurs it.

Appearance: clean, readable, system font stack, comfortable line length,
light and dark via `prefers-color-scheme`. No animation beyond the toggle.
Empty state when nothing matches: "No notes match".

## Decided: Claude's workflow for adding a note

Documented in `CLAUDE.md` so every future session does the same thing:

1. Receive a link or pasted transcript. Save raw material to
   `sources/YYYY-MM-DD-<slug>.<ext>` when there is any.
2. Write `vault/YYYY-MM-DD-<slug>.md` from `templates/note.md`.
3. Run `python3 build.py`; fix any reported error.
4. Tell the owner the note is ready and what the top takeaways are.

For `conversation` notes, step 1 is skipped.

## Decided after builder review (Claude's calls)

- Auto-open the full writeup when every search term matches the note but at
  least one term is absent from title + tags + glance (otherwise the reader
  would see a hit with no visible match).
- `text` also includes `author`, so searching by guest or channel name works.
- All viewer scripts are classic `<script>` tags, never ES modules; Chrome
  blocks module imports from `file://`.
- Front matter values split on the first `:` only, so URLs survive. The
  `## Full writeup` heading match is case-insensitive and trimmed.
- A mismatch between the file-name date and the `date` field is a warning,
  not a failure.
- Tag filter is single-select. The tag list shows every tag across the vault.
- A URL hash pointing at a missing or filtered-out note falls back to the
  newest visible note.
- `sources/` is intended to be committed along with everything else (owner's call when).

## Left to the builder

- Exact CSS, colours, spacing, and the badge styling.
- How `text` is derived for search (stripping Markdown syntax is nice, not
  required).
- Whether `viewer.js` is one file or a few small ones.
- The `marked` version to vendor and how it is fetched (one-time download of a
  single file is acceptable; it is not a "tool").
- Any lightweight checks for `build.py` (a tiny test with a fixture note is
  welcome; a full test suite is not expected).
- A `.gitignore` file may be written (editor junk only; `notes.js` is meant to
  be committed), but the owner decides when and what to commit.

## Open questions resolved during brainstorming

- Framework: none. Owner wants nothing running.
- Where content lives: Markdown files, no database.
- Note depth: skimmable takeaways first, full writeup on click.
- Source link and date visible in the glance header: yes.
- Transcript tooling: deferred; nothing installed for now.
